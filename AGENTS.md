# Безопасная разработка сайта

- Создавайте рабочие ветки от актуальной `main` и открывайте Pull Request в `main` для каждого изменения, включая workflow и настройки публикации. Перед слиянием проверьте diff и дождитесь успешной проверки `Verify site`. Если есть второй сопровождающий, привлеките его к ревью. Откатывайте публикации через Pull Request с `git revert`.
- Публикуйте сайт через GitHub Actions из `main`. В ручном запуске **Verify and deploy GitHub Pages** выбирайте `main`. В настройках окружения `github-pages` оставляйте единственную разрешённую ветку `main`. Для `main` требуйте Pull Request и проверку `Verify site` и сохраняйте запреты на удаление, force push и обход этих правил.
- Сохраняйте текущие URL при изменениях. Проверяйте главную, английскую версию, политики конфиденциальности, `/ozon/` и их ресурсы. При добавлении публичной страницы или ресурса добавьте его в список `files` в `.github/workflows/deploy.yml`.
- Выдавайте каждому заданию Actions только нужные ему права. Закрепляйте используемые GitHub Actions полными SHA из официальных репозиториев. Для кода из Pull Request используйте `pull_request` с доступом на чтение. Не запускайте этот код через `pull_request_target` и не передавайте ему секреты.
- Проверяйте staged-изменения на секреты перед коммитом, например командой `gitleaks git --staged --redact`. Секреты храните в предназначенном для них хранилище. Не добавляйте их в Git, HTML, JavaScript, журналы и артефакты. При утечке немедленно отзовите и замените ключ у поставщика и сообщите владельцу репозитория.
- Считайте весь публичный репозиторий, его ветки, историю и артефакты доступными посторонним. Публикуйте только согласованные с владельцем материалы. `noindex` управляет индексацией `/ozon/`. Для ограниченного доступа нужны приватный источник материалов и проверка прав на стороне сервера.
- Перед изменением настроек публикации или истории сделайте Git bundle из зеркала и проверьте восстановление. Храните резервные копии вне публичного репозитория и артефакта сайта.
